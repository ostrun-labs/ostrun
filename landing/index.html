Le problème

Démarrer un projet avec plusieurs services (auth, mailer, billing...) impose aujourd'hui un choix. Tout écrire à la main, ou adopter une plateforme tout-en-un qui impose sa runtime et son couplage.

Ostrun se place entre les deux. Un point de départ possédé par le développeur, composé de briques indépendantes respectant un contrat commun, sans lien avec Ostrun une fois le code généré.

Principes non négociables

  • Indépendance stricte de chaque service Sa propre base de données, son propre repo, déployable seul.
  • Communication par API ou events uniquement Jamais d'appel direct au code d'un autre service, jamais de base partagée.
  • Polyglotte autorisé Tant que le contrat, manifeste et events, est respecté.
  • Pas de gouvernance runtime La cohérence se fait à la conception, via PR et CI, jamais via un point central en exécution.
  • Secrets jamais en dur .env local ignoré par Git, .env.example committé.

Ce qu'Ostrun n'est pas

  • Pas une plateforme hébergée. Pas de compte, pas de backend Ostrun qui tourne en continu.
  • Pas un PaaS de déploiement. Ostrun génère du code, il ne l'exécute pas pour vous.
  • Pas un outil de synchronisation continue. Une fois généré, un repo vit sa vie.

MVP

  • Gateway. Point d'entrée unique, routage vers les services sélectionnés.
  • Service Auth de référence. JWT, register et login.
  • Bus d'events. RabbitMQ via MassTransit.
  • Docker Compose généré. L'app complète démarre en local en une commande.
