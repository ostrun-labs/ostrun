The problem

Starting a project with several services (auth, notifications, billing...) forces a choice today. Write everything by hand, or adopt an all-in-one platform that brings its own runtime and coupling.

Ostrun sits in between. You get a starting point you own, built from independent services that honor a shared contract, with no tie back to Ostrun once the code is generated.

Non-negotiable principles

  • Strict independence per service Its own database, its own repo, deployable on its own.
  • Communication through APIs or events only Never a direct call into another service's code, never a shared database.
  • Any language As long as the service honors the contract: manifest and events.
  • No runtime governance Consistency happens at design time, through PRs and CI, never through a central service at runtime.
  • No hardcoded secrets A local .env that Git ignores, and a committed .env.example.

What Ostrun is not

  • Not a hosted platform. No account, and no Ostrun backend running somewhere.
  • Not a deployment PaaS. Ostrun generates code, it doesn't run it for you.
  • Not a sync tool. Once generated, the repo is yours to change.

MVP

  • Gateway. One entry point that routes to the selected services.
  • Reference Auth service. JWT, register and login. Still in progress.
  • Event bus. RabbitMQ through MassTransit.
  • Generated Docker Compose. The whole app starts locally with one command.
